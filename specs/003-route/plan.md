## การตัดสินใจทางเทคนิค (Technical Decisions - HOW)
- P-01: ใช้ Redis Geo-Spatial Index ในการจัดเก็บและกรองรัศมีพิกัดไม่เกิน 5 กิโลเมตร ของคำขอขายกับตำแหน่งซาเล้ง -- อ้างอิง REQ-FN-002, REQ-QA-002
  * ทางเลือกที่ปฏิเสธ: Query คำนวณระยะทางตรงจาก RDBMS หลัก (ช้ากว่า และขัดต่อ REQ-QA-002 เรื่องเวลาตอบสนอง <= 3 วินาที)
- P-02: ใช้ Optimistic Locking / Redis Distributed Lock ในขั้นตอนกดรับงาน -- อ้างอิง REQ-BR-002 (BR-02), Q-01
  * ทางเลือกที่ปฏิเสธ: ตรวจสอบสถานะด้วย SELECT ปกติโดยไม่มี Lock (เกิดปัญหา Race Condition เมื่อซาเล้งกดรับพร้อมกัน)
- P-03: ซ่อนพิกัดบ้านเลขที่ผู้ขาย คืนค่าเฉพาะระดับตำบล/แขวง บน API ค้นหา จนกว่าสถานะจะเปลี่ยนเป็น "มีผู้รับงานแล้ว" -- อ้างอิง REQ-SEC-002
  * ทางเลือกที่ปฏิเสธ: ส่งพิกัดละติจูด/ลองจิจูดจริงให้ Frontend ตั้งแต่หน้าค้นหา (ละเมิดความเป็นส่วนตัวผู้ขาย)
- P-04: เชื่อมต่อบริการยืนยันตัวตน Thai-ID / DBD-ID สำหรับลงทะเบียนซาเล้งก่อนเปิดสิทธิ์รับงาน -- อ้างอิง SC-04, REQ-FN-002
  * ทางเลือกที่ปฏิเสธ: อนุญาตให้ซาเล้งรับงานโดยไม่ต้องยืนยันตัวตน (ผู้ขายกังวลเรื่องความปลอดภัยตาม EV-003)
